# 사건명 광고 엔진 — 제품 정의와 운영 문서

> 저장소 소개는 [README](../README.md)에 있습니다. 이 문서는 개발·운영 중에 쓰던 제품 정의 원문입니다.


법률사무소를 위한 자동 사건명 광고 운영·SEO SaaS입니다.

금융사기 관련 사건명을 지속적으로 발견하고, 사건명별 검색 페이지를 법률사무소의 브랜드와 도메인으로 발행하며, 네이버 검색광고 운영과 상담 성과 확인까지 하나의 흐름으로 연결하는 것이 이 프로젝트의 목적입니다.

이 문서는 현재 제품 정의와 저장소 사용법의 정본입니다. 완성 목표, 목표 아키텍처, 데이터 구조, GTM과 단계별 종료 기준은 [`PRODUCT-GOAL-ARCHITECTURE-GTM.md`](PRODUCT-GOAL-ARCHITECTURE-GTM.md)를 제품 전략 정본으로 사용합니다. 과거 설계안, 단계별 계획서와 특정 고객용 pitch는 제품 방향을 정의하지 않습니다.

## 1. 제품 정의

사건명 광고 엔진은 홈페이지 제작 도구가 아닙니다. 새 사건명을 찾은 뒤 페이지 제작, 검색 노출, 광고 준비, 상담 접수와 성과 확인까지 반복되는 업무를 자동화하는 법률사무소용 운영 소프트웨어입니다.

핵심 약속은 다음과 같습니다.

> 새 금융사기 사건명이 검색되기 시작할 때 법률사무소의 대응 페이지와 광고 운영 준비가 이미 갖춰지게 한다.

제품이 판매하는 것은 페이지 개수가 아니라 발견 속도, 발행 속도, 운영 일관성과 데이터 축적입니다.

## 2. 고객과 사용자

### 고객

금융사기 사건을 취급하며 사건명 단위의 SEO와 네이버 검색광고를 운영하려는 법률사무소입니다.

- 구매자: 대표변호사 또는 사무소 운영 책임자
- 일상 사용자: 마케팅 담당자, 사무장, 광고 운영 담당자
- 초기 ICP: 자체 도메인과 네이버 광고계정을 보유하고 금융사기 사건을 반복적으로 수임하는 사무소
- 초기 제외 대상: 금융사기 사건을 취급하지 않거나 자체 상담·광고 운영 의사가 없는 사무소

법률사무소는 다음 자산의 주체입니다.

- 법률사무소 브랜드와 도메인
- 변호사 정보와 상담 연락처
- 네이버 검색광고 계정과 광고비
- 상담 리드와 업무 처리 결과

### 최종 사용자

업체명, 앱 이름, 프로젝트명, 정보방명 등을 검색하는 금융사기 피해자 또는 잠재 상담자입니다.

최종 사용자는 `사건명 광고 엔진`이라는 제품 브랜드가 아니라 고객 법률사무소의 사이트를 봅니다. 제품 브랜드는 영업 사이트, 고객 대시보드와 운영자 화면에만 존재합니다.

### 운영자

중앙 사건명 데이터와 수집 파이프라인을 관리하고, 고객 법률사무소를 개설하며, 페이지·광고·리드 흐름을 지원하는 SaaS 운영팀입니다.

## 3. 해결하는 문제

금융사기 검색 수요는 일반 키워드보다 구체적인 사건명에서 빠르게 발생합니다. 그러나 법률사무소가 이를 수동으로 운영하면 다음 문제가 생깁니다.

- 새 업체명과 프로젝트명을 늦게 발견한다.
- 사건마다 페이지를 복사하고 수정하는 데 시간이 든다.
- SEO 페이지와 검색광고가 서로 다른 작업으로 분리된다.
- 어떤 사건명이 상담을 만들었는지 추적하기 어렵다.
- 고객이 늘어날수록 사이트와 광고 운영이 반복 작업으로 쌓인다.

사건명 광고 엔진은 중앙 데이터 파이프라인을 한 번 운영하고, 고객별 브랜드·도메인·광고계정·리드만 분리하는 멀티테넌트 구조로 이 문제를 해결합니다.

## 4. 핵심 제품 흐름

```text
사건명 발견
  → 중복·노이즈·위험 표현 검토
  → 사건 정보 구조화
  → 사건명별 SEO 페이지 발행
  → 법률사무소별 브랜드와 도메인 적용
  → 네이버 검색광고 등록 계획과 상태 관리
  → 방문·전화·카카오·상담 신청 수집
  → 고객 대시보드에서 사건명별 성과 확인
```

### 중앙 공유 자산

- 사건명과 별칭
- 관측 출처와 발견 시점
- 사기 유형과 진행 방식
- 관련 앱, 플랫폼, 메신저와 인프라 단서
- 페이지와 광고 생성에 필요한 구조화 데이터

### 고객별 자산

- 사무소명, 변호사, 연락처와 프로필
- 도메인과 사이트 형식
- 광고 설정과 광고 상태
- 상담 리드와 전환 이벤트

### 자동화와 승인 경계

- 자동 처리: 사건명 발견, 중복·노이즈 분류, 정보 구조화, 페이지 초안 생성, 리드 귀속과 성과 집계
- 운영자 검수: 근거, 위험 표현, 공개 가능 여부와 데이터 품질
- 고객 승인: 법률사무소 브랜드, 광고 문구, 광고 대상과 예산
- 승인 후 외부 처리: 네이버 광고 실제 등록·집행과 과금
- 고객 업무: 접수된 리드 배정, 상담 상태와 수임 결과 갱신

광고 운영 자동화는 광고 준비와 상태 동기화를 뜻합니다. 실광고 집행과 비용 발생은 고객의 명시적 승인 없이 자동으로 수행하지 않습니다.

## 5. 제품 표면

### 제품 영업 사이트

- `/` — 제품 가치, 작동 방식, 데모와 도입 문의
- `/pricing` — Founding Pilot·Core·Growth·Managed Ops 가격 가설과 도입 문의
- `/portal` — 법률사무소 고객 포털 진입
- `/workspace` — ID 로그인 기반 법무법인 실제 운영실

### 법무법인 생성·설정·화이트라벨 사이트 운영

- `/operator`에서 신규 법무법인, 로그인 계정, 도메인, 브랜드와 기본 사건 편입을 한 번에 생성
- `/d/{token}/site`, `/d/{token}/profile`에서 사이트 형식, 연락처, 변호사와 수행사례 설정
- 공개 준비 조건을 통과한 법무법인만 고객 도메인에서 화이트라벨 사이트 제공
- 모든 법무법인이 같은 애플리케이션과 중앙 사건 데이터를 사용하되 브랜드·상담 동선은 분리

### 피해자용 법무법인 사이트

- `/f` — 사건정보 허브
- `/f/type/{type}` — 사건 유형 허브
- `/f/{slug}` — 사건명별 상세 페이지와 상담 전환
- `/case/{slug}` — 정본 SEO publication. `index` 정책과 canonical URL 사용
- `/response/{slug}` — 정본 광고 랜딩 publication. 항상 `noindex` 정책 사용
- `/lawyers` — 고객 법률사무소 변호사 정보
- `/results` — 고객 법률사무소 수행사례

실제 고객 도메인에서는 위 화면 전체가 해당 법률사무소의 브랜드로 보여야 합니다. 제품 영업용 헤더, 운영 용어와 내부 데이터는 노출하지 않습니다.

### 고객 대시보드

- `/d/{token}` — 운영 개요
- `/d/{token}/activation` — 도메인·광고계정·정책·승인 사건·공개 자산·귀속 활성화 게이트
- `/d/{token}/keywords` — 사건명 커버리지와 상태
- `/d/{token}/search` — URL 색인 상태, 제외 사유, 검색어·노출·클릭·CTR·순위와 refresh 권고
- `/d/{token}/ads` — 광고 설정, 준비와 심사 상태
- `/d/{token}/site` — 피해자용 사이트 형식
- `/d/{token}/profile` — 변호사와 수행사례
- `/d/{token}/leads` — 상담 리드 관리
- `/d/{token}/funnel` — 사건명별 전환 퍼널
- `/d/{token}/reports` — 일일·주간 검색·광고·상담·수임 리포트와 CSV/JSON export

### 운영자 화면과 자동화

- `/operator` — 유일한 운영자 콘솔. 법무법인 생성·활성화, 수집소스·실행, 사건·승인·publication·job·SLA 예외와 GTM 파이프라인 관리
- `/admin` — 별도 화면 없이 기존 주소 호환을 위해 `/operator`로 이동
- `scripts/agent/` — 사건명 수집, 정제, 정본화, 배포 worker, 검색·광고 성과 동기화와 리포트
- `scripts/engine/` — 고객 개설과 legacy 호환 운영 CLI

## 6. 제품의 경쟁력

### 데이터 모트

한 고객을 위해 수집한 사건명과 관측 정보가 중앙 데이터 자산으로 축적되고 다음 고객에게도 활용됩니다. 고객 수가 늘어도 수집 파이프라인을 복제하지 않습니다.

### 발견에서 상담까지 연결

단순한 대량 페이지 생성과 달리 사건 발견, 콘텐츠, SEO, 광고 상태, 리드와 전환 데이터가 같은 사건명 단위로 연결됩니다.

### 고객별 화이트라벨

같은 엔진을 사용하더라도 피해자가 보는 사이트는 각 법률사무소의 브랜드, 도메인, 변호사와 상담 동선을 사용합니다.

### 운영 속도

새 고객이 추가될 때 애플리케이션을 복제하지 않고 고객 설정과 자산만 추가합니다. 중앙 기능 개선은 모든 고객에게 전달됩니다.

## 7. 현재 단계

내부 제품 폐쇄루프는 구현되어 있습니다.

| 영역 | 현재 구현 |
|---|---|
| 사건정보 | 원시 source run/item, legacy keyword→정본 사건 동기화, 별칭·관계·근거 snapshot, 승인·차단 |
| 기회판단 | 출처·속도·검색 노출·CPC·실제 광고 심사·적격상담·수임·고객 정책을 설명 가능한 점수 snapshot으로 저장 |
| 콘텐츠·배포 | SEO와 광고 랜딩을 별도 자산·URL·index 정책으로 관리하고, 품질·브랜드·CTA·canonical 검사 후 공개 |
| 광고 | 고객 승인 정책 안에서 계획·dry-run·실등록 opt-in, 심사 사유와 일별 비용·노출·클릭 GET 동기화 |
| 상담·성과 | session→touchpoint→lead→qualification→consultation→matter outcome 정본 귀속 |
| 고객 제품 | 활성화, 검색, 광고, 리드 상세, 퍼널, 일/주간 리포트와 export |
| 운영 제품 | durable Postgres queue, retry/dead-letter, 승인 큐, publication·SLA 예외, GTM 파이프라인 |
| 데모 | 운영자와 고객 화면이 같은 격리 workspace와 정본 사건 ID를 공유 |

다만 **프로덕션 코드가 존재하는 것**과 **시장 성과가 증명된 것**은 다릅니다. 아직 저장소만으로 완료할 수 없는 항목은 다음과 같습니다.

- target migration을 실제 운영 DB에 적용하고 production deployment를 검증하는 일
- 실제 고객 도메인·TLS·Search Advisor/Search Console·네이버 광고계정 연결
- 고객 승인 하의 제한된 실광고와 비용·심사·상담 귀속 검증
- 한 법무법인에서 30일 운영, 14회 연속 정상 런, 사람 세션·적격 리드 기준선 확보
- 유료 고객, 갱신, 유지율과 운영시간 근거 확보

따라서 현재 판정은 **내부 폐쇄루프 구현 완료, 외부 파일럿 활성화와 시장 증명 전**입니다.

## 8. 현재 최우선 목표

### North Star

> 활성 법률사무소당 월간 귀속 가능 적격 상담 수

현재 출시에 앞선 제품 진실성 게이트는 다음과 같습니다.

> 링크 하나만 전달해도 법률사무소 관계자가 5분 안에 사건 발견→승인→SEO·광고→상담→수임 흐름을 직접 체험한다.

완성된 데모 흐름은 다음과 같아야 합니다.

```text
제품 소개
  → 데모 법률사무소 선택
  → 새 사건명 발견 확인
  → 해당 사무소의 사건 페이지 확인
  → 광고 준비와 상태 확인
  → 상담 리드 발생 확인
  → 고객 대시보드에서 결과 확인
```

### 다음 우선순위

1. 운영 DB에 migration `0009`~`0022`를 적용하고 schema preflight를 통과한다.
2. 한 파일럿 법무법인의 도메인·네이버·검색·전환 자산을 activation 화면에서 모두 `ready`로 만든다.
3. 승인 사건 20건으로 시작해 고신뢰 사건 50~100개 범위를 준비한다.
4. 제한된 실광고와 실제 검색·상담 데이터를 매일 동기화한다.
5. 30일 동안 파이프라인 성공률·귀속률·응답시간·운영시간을 측정한다.
6. GTM 30곳→인터뷰 10건→적격 데모 5건→유료 파일럿 1곳을 실제 기록으로 통과한다.

## 9. 현재 비목표

다음 항목은 필요하지만 현재 제품화 단계의 최우선 과제가 아닙니다.

- 결제와 요금제 자동화
- 셀프 회원가입과 복잡한 권한 체계
- 대규모 고객을 전제로 한 인프라 최적화
- 모든 보안·감사 기능의 선제적 완성
- 고객 승인 정책과 파일럿 근거 없는 자동입찰·예산 최적화
- 다른 법률 분야로의 확장
- 기능 수를 늘리기 위한 관리 화면 추가
- 일반 홈페이지 제작 도구 또는 범용 광고대행 서비스
- 법률 자문, 리드 판매 또는 사건 중개
- 검색 순위, 상담 수 또는 수임 결과 보장

이 항목들은 실제 판매와 고객 사용 흐름이 검증된 뒤 우선순위를 다시 정합니다.

## 10. 제품 완성 기준

다음 내부 조건은 코드와 자동 테스트의 제품화 기준입니다.

- 처음 방문한 법률사무소 관계자가 별도 설명 없이 제품을 이해한다.
- 제품 랜딩에서 실제 데모 전체 흐름으로 이동할 수 있다.
- 고객 사이트는 독립적인 법률사무소 사이트로 보인다.
- 데모 고객 대시보드를 별도 토큰 준비 없이 체험할 수 있다.
- 운영자 화면의 주요 입력과 버튼이 실제 결과를 만든다.
- 하나의 사건명이 수집 데이터, 공개 페이지, 광고 상태, 리드와 퍼널에서 동일하게 이어진다.
- placeholder, 무반응 버튼, 설명용 가짜 입력 폼과 끊어진 링크가 없다.
- 로컬과 배포 환경에서 데스크톱·모바일 핵심 시나리오가 끝까지 동작한다.

실제 프로덕션 완료 판정에는 migration 적용, Vercel/custom-domain 검증과 실고객 파일럿 증거가 추가로 필요합니다. 정적 테스트나 빌드 통과만으로 이 조건을 통과했다고 기록하지 않습니다.

제품화 이후 첫 파일럿에서는 다음을 측정합니다.

- 승인된 사건명이 공개 페이지로 준비되는 데 걸리는 시간
- 사건명·페이지·광고·리드·퍼널 식별자의 연결 정확도
- 상담 리드의 사건명과 유입경로 귀속률
- 핵심 버튼·링크·상태 전환의 오류율
- 기존 수동 운영 대비 사건명 대응 시간 절감

이 수치는 첫 유상 파일럿에서 기준선을 만든 뒤 목표값을 확정합니다. 현재 단계에서는 근거 없는 성과 수치를 제품 약속으로 사용하지 않습니다.

## 11. 체크포인트 기반 3-에이전트 파이프라인

운영 에이전트는 세 개뿐입니다. 예약 실행과 고객 클릭은 별도 에이전트가 아니라 동일한 수집 에이전트의 트리거입니다.

```text
기존 사건명 ─→ 네이버 공식 웹문서 검색 ─→ 반복 노출 신규 소스 후보
                                              ↓
새 수집 후보 ─────────────────→ 2. 파서 생성 에이전트 ─→ 검증된 parserSpec 등록
                                            ↓
매일 예약·고객 클릭 ─→ 1. 수집 에이전트 ─→ 운영 DB
                         최초: 전체수집        ↓ 변경 사건만
                         이후: 체크포인트 증분  페이지·법무법인 후속 처리
                                            ↓ 이상 감지 시에만
                                  3. DB 검토 에이전트(읽기 전용)
                                            ↓ 조치 제안
                                      총운영자 보고·승인
                              승인된 A1 재수집 / A2 재분석만 실행
```

- `agent:collect`: 최초 실행은 빈 체크포인트에서 전체를 수집하고 이후에는 소스별 확정 체크포인트 이후 변경분만 처리합니다. A3의 재수집 제안은 총운영자 승인 후에만 주기 게이트를 한 번 우회하며, 직전 확정 체크포인트는 그대로 보존합니다.
- `agent:discover-sources`: 기존 사건명을 하루 최대 설정 건수만큼 순환 검색합니다. 네이버 공식 Search API 결과에서 법률·피해대응 신호가 있고 서로 다른 사건명에 반복 노출된 도메인만 파서 분석 대기로 등록합니다. 공식 API는 유료광고 여부를 제공하지 않으므로 후보를 광고주라고 단정하지 않습니다.
- `agent:parser`: 신규 URL의 RSS·사이트맵·네이버 블로그·반복 목록 구조를 분석하고 샘플 검증을 통과한 `parserSpec`만 등록합니다.
- `agent:review`: 평소에는 실행되지 않습니다. 수집 실패, 중복, 필수값 누락, 체크포인트 퇴행 또는 파서 실패가 감지될 때만 읽기 전용 보고서와 A1·A2 조치 제안을 만듭니다. 제안은 어드민에서 사유와 함께 승인되기 전까지 소스 설정을 바꾸지 않습니다.
- 승인된 조치는 다음 일일 파이프라인 시작 시 `approved → running`으로 전환되고, A1·A2 실행 결과를 `completed | failed`로 같은 승인 원장에 되돌려 기록합니다. 거절 제안은 실행되지 않습니다.
- `daily-supervisor.sh`: 매일 08:47 동일 수집 에이전트를 실행합니다. 실패 시 15분 뒤 재시도하지만 15분 주기 수집 에이전트는 없습니다.
- `click-collection-daemon.sh`: 고객의 수집 버튼을 DB 알림으로 받아 같은 수집 구성요소를 승인 소스·해당 법무법인 범위로 즉시 실행합니다.
- `pipeline-lock.sh`: 예약 트리거와 클릭 트리거가 동시에 `data/keywords.json`과 DB를 쓰지 않게 합니다. 예약 작업은 진행 중인 클릭 작업이 끝나기를 기다립니다.
- 수집은 체크포인트 후보만 만들며, DB 적재와 변경 사건 페이지 갱신이 성공한 뒤에만 확정 체크포인트로 승격합니다.
- 실행 manifest에는 `checkpointBefore`, `checkpointCandidate`, `checkpointCommitted`, `changedCaseIds`가 기록됩니다.
- 같은 날 재시도에서는 이미 생성된 LLM 추출 결과를 재사용합니다.
- DB 동기화, 전체 고객 편입 또는 demo 전량 검증이 실패하면 성공으로 기록하지 않습니다.
- 기본값은 광고 dry-run입니다. 실제 등록은 `ENGINE_LIVE=1`과 `TARGET_AD_AUTOMATION=1`, 검증된 고객 계정, 고객이 승인한 사건·행동·예산 정책을 모두 통과할 때만 실행됩니다.
- 일일 시작 시 target schema 29개 핵심 relation을 검사하며, migration 누락을 성공 런으로 기록하지 않습니다.

운영 정본은 로컬 `agent.log`와 DB `agent_runs`입니다. 성공 런에는 `pipeline-result: success`가 존재하며, demo 배포 수와 기대 수가 같고 `adEnabled=0`이어야 합니다.

## 13. 로컬 실행

```bash
npm install
npm run dev
```

기본 주소는 `http://localhost:3000`입니다.

검증 명령:

```bash
npm test
npx tsc --noEmit
npm run build
```

일원화된 운영 명령:

```bash
npm run schema:core:check        # 실제 운영 정본 스키마 확인
npm run pages:refresh            # 키워드·관측 → 랜딩 페이지 갱신
npm run workers:collection       # 법무법인 수집 요청 완료 처리
```

정본 흐름은 `수집소스 → 키워드·관측 → 사건 랜딩 → 법무법인별 광고 O/X → 방문·문의`입니다.
별도의 목표 모델 파이프라인은 정기 수집과 운영 화면에서 실행하지 않습니다.

`npm run db:generate`는 migration 파일만 생성합니다. 운영 DB 적용(`db:push` 또는 별도 migrate)은 외부 상태 변경이므로 배포 절차에서 명시적으로 수행합니다.

DB가 필요한 화면과 자동화 스크립트는 환경변수 설정이 필요합니다. 실제 비밀값은 저장소에 기록하지 않습니다.

## 15. 앞으로의 의사결정 원칙

- 고객이 보고 체험하는 완성도를 내부 구조보다 먼저 판단한다.
- 새로운 기능보다 끊어진 기존 흐름을 먼저 완성한다.
- 피해자용 사이트와 SaaS 제품 UI를 명확히 분리한다.

- 실제 외부 상태 변경, 광고 과금과 도메인 전환은 명시적 승인 후 수행한다.
- 구현 현황과 실행 방법이 달라지면 README를, 제품 목표·아키텍처·GTM 결정이 달라지면 `PRODUCT-GOAL-ARCHITECTURE-GTM.md`를 갱신한다.
- 과거 계획서를 새 정본처럼 증식시키지 않는다.
