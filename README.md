# 사건명 광고 엔진

법률사무소를 위한 검색광고·SEO 자동화 서비스입니다. 새로 검색되기 시작한 금융사기 사건명을 자동으로 찾아내고, 법률사무소별 브랜드와 도메인으로 사건명 페이지를 발행하고, 네이버 검색광고 운영과 상담 접수까지 하나의 흐름으로 잇습니다.

> **공개본 안내** — 이 저장소는 포트폴리오용 공개본입니다. 고객 법률사무소·변호사·경쟁사 이름, 연락처, 도메인은 가상 값으로 바꿨고, 고객 제안 자료·이미지는 포함하지 않았습니다. `data/keywords.json`은 실제로 수집한 사건명 약 2만 8천 건이며, 출처로 쓴 법률사무소 이름과 주소만 가상 값입니다. 코드와 테스트 안의 예시 사건명은 가상 이름입니다. 사건명은 공개 웹에서 수집한 검색 키워드일 뿐이며, 해당 업체가 사기라는 판단이나 주장이 아닙니다.

## 어떤 문제를 풀었나

금융사기 피해자는 "투자 사기" 같은 일반 단어보다 자기가 당한 **업체 이름이나 앱 이름**으로 검색합니다. 이런 사건명은 매일 새로 생기고, 검색이 몰리는 기간은 짧습니다. 법률사무소가 이를 손으로 따라가면 네 가지가 어렵습니다.

- 새 사건명을 늦게 발견합니다.
- 사건마다 페이지를 복사하고 고치는 데 시간이 듭니다.
- 검색 노출과 검색광고가 따로 움직입니다.
- 어떤 사건명이 실제 상담으로 이어졌는지 추적하기 어렵습니다.

그래서 수집은 한 번만 중앙에서 돌리고, 법률사무소마다 브랜드·도메인·광고 계정·상담 데이터만 나눠 쓰는 구조로 만들었습니다.

## 동작 흐름

```text
수집 소스 20개  →  사건명·관측 기록  →  사건명 페이지  →  사무소별 검색광고  →  방문·상담 접수
(뉴스, 커뮤니티,     (중복 제거,          (사무소 브랜드와      (키워드 등록, 입찰,     (암호화 저장,
 공개 사이트맵)      유형 분류)           도메인으로 발행)      운영 시간, 성과 수집)    알림, 대시보드)
```

## 한 일

### 1. 사건명 수집 파이프라인

- 뉴스 RSS, 피해자 커뮤니티, 공개 사이트맵에서 사건명 후보를 수집합니다 (Python).
- 같은 사건의 다른 표기를 하나로 묶고, 무작위 문자열·도메인 조각·일반 명사 같은 잡음을 걸러 냅니다.
- 같은 운영 주체의 여러 사이트를 한 출처로 묶어, 독립된 출처 수를 과장하지 않게 했습니다.
- 네이버 검색 결과에서 새 수집 소스를 찾아 등록 후보로 올리고, 사람이 승인한 것만 반영합니다.
- 수집 진행 위치를 저장해 두어, 중간에 끊겨도 이어서 수집합니다.

### 2. 멀티테넌트 페이지 발행

- 접속한 도메인과 서브도메인으로 어느 사무소의 어느 사건 페이지인지 판별합니다.
- 사건명마다 서브도메인을 배정해 검색 엔진에 독립된 페이지로 노출합니다.
- 사무소별로 변호사 정보, 연락처, 디자인 템플릿을 바꿔 같은 사건 데이터를 다른 사이트로 보여 줍니다.
- 사이트맵과 구조화 데이터, 표준 URL을 사무소 단위로 생성합니다.

### 3. 네이버 검색광고 연동

- 사건명을 광고 키워드로 등록하고, 심사 결과와 노출·클릭·비용을 주기적으로 가져옵니다.
- 사무소가 정한 운영 시간에 맞춰 광고를 켜고 끕니다.
- 광고 계정의 API 키는 AES-256-GCM으로 암호화해 저장합니다.
- 실제 등록·변경은 사람의 승인을 거친 작업만 실행합니다.

키워드 관리와 자동 입찰 부분은 별도 저장소로 분리했습니다: **[naver-powerlink-engine](https://github.com/limvest/naver-powerlink-engine)**. 실제 검색 결과에서 광고 순위를 관측해 입찰가를 조정하는 자동 입찰 프로그램은 그 저장소에만 있고, 이 저장소에는 키워드 등록·심사·운영 코드와 입찰 기준 금액 설정만 있습니다.

### 4. 상담 접수와 대시보드

- 상담 신청의 이름·연락처·내용을 암호화해 저장하고, 텔레그램으로 알립니다.
- 같은 상대방이 이미 접수돼 있는지 이해충돌 여부를 확인합니다.
- 사무소 담당자는 대시보드에서 키워드, 광고 상태, 상담 목록을 봅니다. 운영자 화면에서는 전체 사무소와 수집 소스를 관리합니다.
- 방문과 상담이 어느 사건명 페이지에서 왔는지 기록합니다.

### 5. 광고 문구 규정 점검

변호사 광고 규정에서 문제 삼는 표현("보장", "100%", "승소율", "최고", "무료" 등)이 광고 문구에 들어가면 등록 전에 걸러 냅니다. 실제 회사 이름을 도용한 사칭 사건 페이지에는 "이름이 같은 정식 등록 업체와는 무관하다"는 안내 문구를 붙입니다.

### 6. 서버 배포와 운영

- Docker Compose로 웹 서비스, PostgreSQL, 수집기를 분리해 한 서버에서 운영했습니다. 외부 접속은 Cloudflare Tunnel을 거칩니다.
- 수집, 광고 성과 동기화, DB 백업, 저장 공간 정리, 운영 보고를 systemd 타이머로 예약 실행했습니다.
- 접근 로그를 수집해 이상 징후를 알리는 보안 모니터링을 붙였습니다.
- 배포, 복구, 보안 점검 절차를 문서로 남겼습니다.

## 저장소 구성

```text
app/                 화면과 API 라우트 (Next.js App Router)
src/domains/         수집 → 기회 판단 → 콘텐츠 → 발행 → 광고 → 상담 → 성과 도메인 로직
src/lib/engine/      사무소별 브랜딩, 네이버 광고 연동
src/lib/scam/        사건명 데이터와 페이지 생성
src/lib/leads/       상담 접수, 이해충돌 확인, 요청 제한
src/platform/        작업 큐와 외부 연동 어댑터
scripts/agent/       사건명 발견·수집·정제 (Python, TypeScript)
scripts/engine/      사무소 개설과 광고 운영 명령
drizzle/             데이터베이스 마이그레이션
deploy/a1/           Docker Compose, systemd 서비스·타이머, 백업·보안 모니터링
data/                수집 사건명 데이터와 수집 소스 설정
tests/               단위·통합 테스트
```

## 실행

```bash
npm install
npm run dev          # http://localhost:3000

npm test             # 테스트 955개
python3 -m unittest discover -s scripts/agent -p 'test_*.py'   # 수집기 테스트 77개
```

데이터베이스가 필요한 화면과 자동화 스크립트는 `.env.example`의 환경변수를 채워야 동작합니다. 테스트는 내장 PostgreSQL(PGlite)로 돌아가므로 별도 DB 없이 실행됩니다.

## 배운 점과 한계

- **수집 데이터에는 잡음이 많이 섞입니다.** 사건명 후보에 무작위 문자열, 도메인 조각, 일반 명사가 함께 들어옵니다. 걸러 내는 규칙마다 테스트를 두어 기준을 고정했습니다.
- **출처가 많아 보이는 것과 독립된 출처가 많은 것은 다릅니다.** 한 운영 주체가 여러 도메인을 쓰는 경우가 많아, 출처를 묶는 기준을 따로 두었습니다.
- **돈과 외부 계정이 걸린 작업은 사람의 승인을 거치게 했습니다.** 광고 등록, 소스 추가, 운영 DB 변경은 자동으로 실행하지 않고 승인 대기 목록에 올립니다.
- **구현과 검증을 구분해 기록했습니다.** 테스트가 통과한 것과 실제 시장에서 확인된 것을 같은 것으로 적지 않으려고 구현 현황 문서를 따로 두었습니다.
- **테스트 955개 중 7개는 실패 상태입니다.** 쿠키 처리 1개, 사건 페이지 렌더링 4개, 수집 소스 발견 2개이며 운영 종료 시점에 고치지 못한 채 남았습니다.
- **공개본은 그대로 실행하면 일부 이미지가 비어 보입니다.** 고객사 사진과 로고를 뺐기 때문입니다.
